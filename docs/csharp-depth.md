This expansion delivers **54 topics, 112 practical cards, 54 independent overviews and 30 lessons**. Existing topic/card/lesson IDs and their state are preserved. New topics each have at least two different tasks; legacy topics gain domain or semantic variants. Counts describe inventory, not a quality score.

## Supported runtime and scope

SDK **10.0.402**, C# **14**, net10.0, ASP.NET runtime/testing **10.0.13**, EF Core SQLite **10.0.13**, xUnit **2.9.3**, VS adapter **3.1.4**, Test SDK **17.14.1**. The existing toolchain stays unchanged; EF SQLite is the only new direct package. Its real SQLitePCL native provider, EF dependencies and Microsoft.Data.Sqlite are captured in all four NuGet locks. Tests enable foreign keys on each fresh in-memory **relational SQLite** connection; these are disposable real SQLite databases, not EF InMemory. This single-connection setup models stale sequential writers, not production parallel-writer throughput or network/database availability. SQLite does not implement SQL Server rowversion; Version is application-managed. Migrations, dotnet-ef commands and host/package layout stay in [tooling](../playground/csharp/tooling.md).

Framework-provided JSON, HTTP, DI/options/logging, LINQ, channels and ASP.NET APIs require no added runtime packages. Explicit usings appear in cards; basic System, IO, Collections.Generic, Linq, Net.Http, Threading and Tasks imports come from the playground's enabled implicit usings. Place reusable examples in Library, request/xUnit cards in Tests. Companion types are named in explanations; all snippets compile together in the supplied fixture. Standalone extraction requires copying those dependencies too.

The selected ecosystem covers serialization, HTTP, local APIs, relational data and testing. [EF's maintained SQLite provider](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/) supplies genuine constraints/transactions; [ASP.NET fundamentals](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/?view=aspnetcore-10.0) supplies DI/options/logging without inventing a framework. UI categories remain intentionally bounded: [Blazor](https://learn.microsoft.com/en-us/aspnet/core/blazor/?view=aspnetcore-10.0), [MAUI](https://learn.microsoft.com/en-us/dotnet/maui/what-is-maui?view=net-maui-10.0), WPF/WinForms, authentication/authorization, distributed resilience, PostgreSQL/SQL Server provider differences and production migrations are separate expansions. This is a supported-scope choice, not a claim that these categories are unimportant or that the current pack is exhaustive.

## Reproduce

Follow [playground setup](../playground/csharp/README.md). After the first network-dependent SDK/NuGet/Node provisioning, checks use local/in-process data and transports. A cold machine still needs dependency downloads; locked restore may contact configured NuGet sources. No credentials, public HTTP calls, production database or deployment is required by behavior tests.

```sh
source ~/.config/nvm/nvm.sh
nvm use
pnpm install --ignore-scripts
pnpm test
pnpm check:csharp
pnpm audit:coverage --check
node scripts/lesson-coverage.cjs --check
pnpm audit:runtime csharp > /tmp/syntaxiser-runtime-csharp.json
```

The runtime report includes the audited Git revision and hashes, while check:csharp prints Node and dotnet --info. Save it outside the repository; generated source, TRX and bin/obj are ignored. Build/report checks must pass, and the JSON common audit must have zero C# findings while preserving other languages' unresolved findings.
