# How Syntaxiser works

Syntaxiser supports learning programming languages while writing real code. Contextual examples connect a task to an approach; separate topic overviews explain the syntax and rules behind it. Search helps learners ask in their own words, and pins keep useful examples available for repeated practice. These learning goals guide content and retrieval across every supported language and developer tool.

## Content design: quick reference and contextual snippets

Syntaxiser has two distinct content purposes that help learners move between understanding a topic and applying it. This distinction applies to every supported and future language, including library and tooling content:

- **Topic quick reference:** A concise, structured overview of a topic's syntax. Cover its main forms, variations, and essential rules with minimal syntax examples and brief explanations. Readers should be able to understand the topic's syntax without piecing together practical examples. For loops, this means an overview of `loop`, `while`, and `for`, including `break`, `continue`, labels, and loop return values where applicable.
- **Contextual snippets:** Practical, real-world examples of using syntax to accomplish a task. Select these by editor context or search intent; they illustrate application rather than provide a complete topic overview.

Clicking a reference topic should open its dedicated quick-reference overview. Filtering existing snippets by topic does not fulfill this requirement. A snippet's reference action should link to the relevant overview; when several topics apply, make each overview reachable. Related practical examples may supplement an overview, but should remain distinct from its core syntax content.

Maintain topic overviews separately from contextual snippet content, linked through stable topic identifiers. Review overview coverage against the topic's syntax forms and rules; review snippets for practical usefulness and relevance. The Rust browser loads 115 dedicated overviews from `packs/rust-reference.json`, separately from contextual cards in `packs/rust.json`. Each overview contains a summary, schematic syntax forms, and essential rules; it is linked through its concept ID and validated at activation. The browser renders overviews directly and does not substitute contextual snippets when overview content is missing.

[Back to the learning and setup guide](../README.md).

Overview content is independently authored with checks against the [Rust Reference](https://doc.rust-lang.org/reference/), [standard library](https://doc.rust-lang.org/std/), [Axum 0.8](https://docs.rs/axum/0.8.6/axum/), and framework documentation. Library-specific topics explicitly identify their framework; overview fragments use schematic type/value names and are not standalone programs.

The Reference tree stays fully expanded in a bounded scrollable pane, including after topic selection. No group-expansion clicks are required. Context also offers up to two quick-reference previews, ranked directly from concept matches: cursor word (65%), current line (25%), and nearby code (10%). Only topics with dedicated overview content and sufficient context evidence are offered; scope defaults, imports, and edit history do not create topic suggestions. Unsupported editors clear those suggestions. Previews have a separate heading and accent edge, show three syntax lines in a scrollable viewport, and link to the full dedicated overview. They do not count toward the example-card budget or enter the practical-example pin collection.

Manual search ranks overviews separately from examples. Overview scores combine 80% concept weight with 20% query-word coverage across title, summary, syntax, and rules; lexical coverage contributes only when at least half of the non-stop query words match. If the query recognizes concepts, unrelated overviews are excluded even when their text mentions the query. Without recognized concepts, sufficient overview-text coverage can still surface a result. Only the top two previews appear; the complete catalog remains available in Reference. Pending or stale search responses never show cursor previews for a different query, and clearing search restores the current editor's previews immediately.

## Retrieval

The Rust pack contains **277 cards across 115 concepts**, stored in `packs/rust.json`. Searchable metadata includes topics, keywords, scopes, priority, and titles; the card UI renders only `code`. Optional `explanation` metadata supplies plain text for hover tooltips and accessibility descriptions and does not affect search ranking. Packs without explanations continue to work. Content is independently curated from common Rust syntax rather than fetched from documentation.

Coverage includes ownership, borrowing, lifetimes, strings and Unicode, arrays and slices, tuples, pattern matching, Option and Result combinators, iterators, vectors, maps, sets, queues, sorting, numeric operations, traits, conversions, const generics, macros, attributes, tests, file and buffered I/O, paths, command-line arguments, threads, channels, atomics, async syntax, TCP/UDP networking, HTTP clients, and web servers.

Core syntax also includes arithmetic, comparison, boolean and bitwise operators; block values and semicolons; early return, unit and never types; while/continue and labelled loops or blocks; destructuring assignment and let chains; function pointers, closure bounds, returned closures and async closures; const functions and inline const; generic data types and default type parameters; supertraits, default methods, generic associated types and lifetime bounds; type aliases, turbofish and qualified paths; enum discriminants, raw identifiers, unsafe functions, raw pointers, unions and C ABI declarations. Unsafe examples describe their validity requirements in the hover explanation.

The let-chain card requires Rust 1.88+ and edition 2024; async closures require Rust 1.85+. These requirements appear in the corresponding explanations. The FFI example declares a native C function that must be supplied at link time. The pack is a practical reference for common stable syntax, not an exhaustive Rust language specification.

Web references include Axum 0.8 and Actix Web 4 server startup, routes, JSON handlers, path/query parameters, shared state, responses, and middleware. The code names the libraries it uses. Those cards require the corresponding crates in the user's project; serde examples need its derive feature, Reqwest JSON examples need its json feature, and Tokio examples need the runtime/net/io/signal features they use. The extension itself installs none of these crates.

This MVP uses deterministic **concept embeddings**, not pretrained neural embeddings. Each curated language concept forms a vector dimension. Natural-language aliases and syntax patterns encode queries, and weighted topic metadata encodes cards. Cosine similarity combines with TF-IDF lexical similarity. Automatic ranking additionally weights cursor-line code, nearby code, enclosing symbols, imports, recent edits, and scope. Diversity scoring reduces repeated topics. Empty or unrecognized manual queries produce no results.

Manual search counts each recognized alias concept once, using syntax patterns only when no alias matches that concept. This prevents a word such as “string” from gaining extra weight simply because it also names a Rust type. The score combines 72% concept similarity with 28% lexical similarity over titles, keywords, and code, then scales it by concept coverage: a card covering all recognized concepts keeps its full score, while partial matches receive less weight. For example, “string arrays” prioritizes examples tagged with both strings and arrays. Syntax patterns still support queries such as `&[T]`, and cursor-based ranking retains its separate syntax weights.

This is fast and offline, but semantic coverage depends on both the reference content and the aliases in the pack. It cannot invent examples for a topic absent from the pack; arbitrary paraphrases may also need additional aliases. `SemanticEncoder` is replaceable with a local neural encoder, provided it supplies compatible vectors for cards and queries; no model is included in this MVP.

The controller retrieves up to sixty candidates per section. The webview renders the configured initial page and appends more on demand, keeping the existing highlighted nodes intact. A new result set resets that section's page; search and automatic reference expand independently.

Use the pin icon on any contextual or search card to keep it in **Pinned**, above the active results. Pins stay available across cursor movement, file/language changes, and searches. A pinned card appears once, rather than repeating in the result list. Click its pin icon again to remove it. Each pin has an expand/collapse arrow; collapsed pins show their first code line. Click the **Pinned** heading to collapse or expand the entire group. Pins do not count toward the initial result-page size.

Pin identifiers and collapse preferences are saved locally per VS Code workspace and survive window reloads. Stored identifiers include the language, and pinned code is resolved from the current reference pack when the extension starts. Removed cards are ignored; updated snippets use the new curated content. Closing and reopening the sidebar preserves pins and their collapse state.

Cursor and edit events are debounced by 350 ms. Repeated movement within the same word and line is ignored. Recent edits are per document, limited to eight entries, and expire after 45 seconds. Symbol results are cached per document version for 15 seconds, with an 800 ms timeout and stale-response guards. Hidden views skip retrieval until reopened. All source context stays in extension-host memory; only reference cards and UI state reach the webview. The manual search text is retained in VS Code's webview state; pin identifiers and collapse preferences use local workspace storage.

The scanner handles strings, raw strings, char literals, lifetimes, and nested comments. It is a lightweight fallback, not a Rust parser. Work is bounded to 180 KB before and 16 KB after the cursor; on very large files whose containing declaration is outside that window, language-server symbols improve scope accuracy. No project-wide scan is performed. Bounded direct/grouped/aliased use paths expand imported namespace prefixes for library retrieval; glob imports, local shadowing and cross-file re-exports are not resolved.

## Syntax highlighting

The webview bundles Highlight.js core and locally registered Rust, Go, TypeScript, JavaScript, Python, Java, HTML, CSS, SQL, shell and TOML grammars. Keywords, types, functions, literals, attributes, and macros receive token colors. Palettes follow VS Code's light, dark, and high-contrast theme classes and adapt when the theme changes; custom TextMate token overrides are not imported. Code remains selectable as plain text when copied. Unknown language grammars fall back to plain text.

Highlighting runs only when a card's content or language changes. The renderer starts from text nodes, and the highlighter escapes markup before adding token spans. Everything loads from extension-local resources under the existing content security policy. Third-party license terms are included in `THIRD_PARTY_NOTICES.md`.

## Lessons and progress

`src/lessons/catalog.ts` contains separately authored exercises for Rust and Go, with stable IDs and five ordered difficulty levels. Each exercise defines instructions and an observable completion check. Built-in lessons omit code snippets entirely rather than repeating the task in a comment-only block; catalog tests guard against redundant snippet content. The AGENTS authoring rule prohibits solutions or implementation scaffolding in lesson snippets. Completion checks describe observable outcomes without providing solutions. Lessons are self-assessed tasks: they do not execute code, grade answers, or enter contextual/reference retrieval. Keep the syntax overviews and practical reference snippets separate from these exercises.

`LessonStore` validates versioned workspace data and stores progress by language and lesson ID. Built-in content is resolved from the current catalog; only custom lessons and tracked statuses are persisted. Unknown/retired IDs, invalid fields, duplicate custom IDs, and unsupported schema versions are ignored. Host message validation bounds strings, difficulty, and IDs; custom lessons are capped at 200 per language. Saves are serialized using independent snapshots, with visible host errors if persistence fails.

Lesson tracker and Lesson browser follow the sidebar state's canonical language context, including editor aliases and terminal context. There is no independent language selection or saved language override. The legacy saved `lessons` mode now opens Lesson tracker; `lesson-browser` opens the browser. Shared compact controls filter difficulty/status, sort difficulty, and hide completed tasks. Three direct status buttons change a task in one click; clicking the selected status untracks it.

Lesson tracker shows only tracked work, ordered In progress, To do, then Done, with the Hidden filter available for restoration. Untracked catalog lessons belong in the browser. Difficulty sorting applies within each tracker group. These groups remain separate from snippet pins. Tracker cards show a 240px preview and Show more only when measured content overflows. A shared resize observer updates overflow controls as the sidebar or visible tab changes.

Lesson browser uses a bounded two-column layout like Reference: expanded difficulty groups and nested title lists on the left, full selected lesson content on the right. Native buttons provide keyboard navigation; selection focuses the content heading without scrolling away the tree. Selection IDs are retained per language in webview state. Catalog filters apply to the tree and selected content; hidden lessons require the explicit Hidden filter. Browser and tracker reuse the same card renderer and host actions, so status changes, personal edits, and resets remain consistent. The browser shows full content without preview truncation and retains scroll position during status updates.

Cards expose their status with a text/symbol badge, theme-aware accent border, and subtle tint. The `hidden` status is persisted through the same validated storage/message path as other progress. Hidden lessons are excluded from normal filters and the completion denominator; only the explicit Hidden filter displays them. A direct hide/restore button changes between hidden and untracked, and normal status buttons can also restore a hidden lesson to that state. Reset progress clears hidden statuses too. This is separate from the temporary Hide done display preference.

Custom forms have only title and description. New personal lessons default to To do in the host store and show a Your lesson label with a dashed outline; edits preserve their current status. New lessons use the difficulty selected when the form opens, or level 1 for all levels. Optional stored starter code and completion checks may be empty; editing older personal lessons retains their existing metadata. Custom forms preserve unsaved text during editor updates and retain their original language and difficulty when context or filters change. Language-specific or global resets require a VS Code confirmation and can optionally delete custom lessons; deleting an individual custom lesson also requires confirmation. Built-ins cannot be edited or deleted.

Run `pnpm test` for lesson catalog integrity, omission of built-in snippets, active-language switching, tracker/browser separation, difficulty-tree coverage, selection restoration, shared status actions, WIP ordering, personal task defaults/markers, malformed storage/messages, per-language status and custom CRUD persistence, hidden status restoration/reset, visual status markers, rendering/filtering, keyboard focus, and HTML escaping. Manually exercise the browser/tracker, reload, custom-form, and reset workflow documented in the README in an extension host. Completion checks tell the learner how to verify their solution.

## Add a language

Language packs can supply optional `referenceGroups` metadata: an ordered list of groups with `id`, `title`, and concept IDs in `topics`. Optional `referenceTopics` contains overviews with `id`, `title`, `summary`, `syntax`, and `rules`, linked by concept ID. Ungrouped concepts appear under Other topics; missing overview content is explicitly marked as unavailable. Future language and library catalogs should keep the same content distinction.

Every bundled topic overview must include a nonempty `references` list of `{ "title": "Descriptive source name", "url": "https://…" }` entries. Choose topic-specific official documentation, maintainer API guides, or other high-quality learning sources, including the libraries used by the topic. These links appear under **References** after the existing syntax and rules; contextual examples link to the same full overview. Do not replace authored content with links or put source URLs in copied code. Existing optional metadata remains compatible with older packs, but catalog tests require sources for every bundled overview. Titles are plain text; only HTTPS links without embedded credentials are accepted.

Before adding or changing a source, read the destination to confirm it teaches the topic and run `pnpm check:references`. This explicit online check follows redirects, requires a successful HTTP response, and checks fragment IDs in returned HTML, fetching shared documents once. It is separate from offline builds and tests; a successful response checks reachability, not the correctness of an external page. Recheck periodically because documentation paths can change. The extension itself fetches nothing; selecting a reference link opens it through VS Code's normal external-link handling and needs internet access.

1. Add a JSON pack following `packs/reference-pack.schema.json`: concepts with aliases and syntax patterns, and concise code cards with matching topic IDs. Each card may include a nonempty, plain-text `explanation` for its hover tooltip.
2. Add a `LanguageAdapter` in `src/languages` that produces the generic `EditorContext` shape.
3. Load and validate the pack in `src/extension.ts`, register the adapter with `ReferenceController`, and add the `onLanguage` activation event to `package.json`.
4. Import and register that language's highlighting grammar in `src/webview/highlight.js`, then rebuild with `npm run compile`.
5. **Required:** add a runnable `playground/<language>/` project with representative cursor contexts and a README explaining setup, execution, search/reference checks, and switching languages with retained pins. Type-check or compile it and run it before submitting the language-support PR. Link it from the support documentation; a short tour in `examples/` supplements this playground.
6. **Required:** include widely used, maintained libraries in every new or expanded language catalog. Review current ecosystem usage across relevant application areas, record the selected packages, versions, and primary sources, and provide useful practical examples plus separate syntax/API overviews for each. Make them searchable by library/task and relevant to imported APIs; validate examples against real package types and add runnable playground checks for their main workflows.

The controller, retrieval engine, and sidebar are shared. Search uses the active supported language; with no supported editor, it retains the last supported pack (Rust by default). Go uses VS Code’s `go` language identifier and activates on `.go` files. TypeScript uses `typescript` and the adapter alias `typescriptreact` for `.ts` and `.tsx` files; both share one catalog and canonical TypeScript pin identifiers. Unsupported languages show an explicit empty state for automatic reference.

The TypeScript scanner masks comments, escaped quotes, template literals, and common regex literals while preserving offsets. It recognizes function and arrow bodies, class methods, interfaces, type aliases, and enums, and retains module specifiers from real import declarations. VS Code document symbols refine scope when available. ## Terminal context

The stable VS Code 1.93 terminal shell integration API drives a separate `shellscript` pack. Active-terminal changes and active-terminal execution start/end events select terminal mode; editor activation/selection restores document context. An explicit Use Active Terminal Context command covers focus changes that the public API does not report. Startup activation makes terminal-only workspaces available. Commands in background terminals update their own in-memory cues without replacing the selected context; terminal closure removes those cues. Hidden sidebars refresh when reopened, and generation guards invalidate pending document-symbol results when switching sources.

Only a bounded, allowlisted set of command names and known subcommands enters retrieval. Arguments, terminal output, working directories, and raw history are neither published nor persisted. This is a lexical cue extractor, not a complete shell parser: complex quoting, wrappers, aliases, scripts, and unrecognized commands can yield generic or incomplete suggestions. Terminal execution events contain executed commands rather than live unfinished input. For new Zsh terminals, a ZLE line-pre-redraw/line-init hook supplies live allowlisted tool/subcommand cues via private temporary files. The extension injects a temporary ZDOTDIR through its nonpersistent environment collection, sources the normal user startup files, and restores the user ZDOTDIR. The watcher validates file names, bounds payload size, matches the shell process ID to a terminal, and feeds the regular debounce path. Only the active terminal can select live context. Clearing the command restores generic suggestions; nonempty cues use search retrieval to narrow examples. Arguments and raw buffers never cross the bridge. This works before Enter and requires recreating existing terminals after reloading. Other shells retain execution-event support. Missing shell integration displays a fallback message with searchable generic examples. The curated examples and syntax overviews remain separate in `packs/shellscript.json` and `packs/shellscript-reference.json`.

## YAML schema context

The controller passes an optional document path to adapters. YAML uses workflow/Compose/template filenames and masked root keys to infer an ecosystem. Its tolerant scanner preserves offsets, quoted mapping keys, intrinsic tags and explicit expressions while masking comments, quoted prose and multiline block bodies. It collects the current line and enclosing indentation path within the active YAML document. Old edits and language-server symbols are excluded from YAML context.

Optional `EditorContext.topicPrefixes` limits contextual examples and quick references to allowed topic families; adapters that omit it retain existing behavior. YAML allows foundations plus the detected schema, or foundations alone for generic files. Search and reference browsing retain the full pack, and pins resolve from that complete pack with stable YAML identity. The extension uses no YAML parser or schema service at runtime. See [coverage and limitations](yaml-support.md) and the [runnable validation/manual guide](../playground/yaml/README.md).

## SQL dialects and host clients

The SQL adapter masks literals, quoted identifiers, comments (including nested block comments) and dollar-quoted PostgreSQL bodies with stable offsets. It selects the current semicolon-delimited statement; symbol names and old edit fragments are omitted because they can reintroduce masked or unrelated SQL. Extraction is lexical and bounded by the controller's existing document window. It does not query schemas or execute SQL.

`syntaxiser.sqlDialect` is a resource setting, defaulting to `sqlite`. The controller caches a derived SQL pack/retriever for each dialect. Optional validated `dialects` metadata filters examples and overviews, and unavailable concepts/groups are removed before retrieval. Shared content omits that metadata. The displayed language includes the selected dialect. Search is recomputed on settings changes. Pins resolve against the full pack, so stable `(sql, cardId)` identity survives dialect changes; explicitly labelled pins saved in another dialect remain visible intentionally. This also preserves per-language SQL lesson progress.

`withSqlCompanions` adds independently authored client topics from `packs/sql-companions.json` to Go and TypeScript during activation, retaining all existing IDs. Python's sqlite3 companion merges through the same hook into the Python catalog. These examples never enter SQL results. Keep additional client coverage in host-language catalogs; reserve SQL for queries and database concepts.

`pnpm check:sql` compiles the extension and executes exact catalog code against SQLite 3.53.1 and native PostgreSQL 18.4, then exercises Python sqlite3, strict TypeScript pg and Go database/sql clients. Dependency locks, seeded schemas, exact result assertions, NULL/constraint/rollback probes and setup/manual instructions live in [playground/sql](../playground/sql/README.md). Extension regressions cover extraction, natural queries, dialect filtering, activation, highlighting, copy text, pins, settings refresh and language switching. Five stable SQL lesson IDs form a starter path; #36 owns further progression.

## Java catalog and context

Java activation registers its lexical adapter, separate practical/overview catalogs and bundled highlighting grammar. The adapter preserves source offsets while hiding comments, literals and text blocks, infers brace scope during incomplete edits and uses VS Code document symbols when available. Explicit imported type/static-member paths reinforce identifiers used on the current line.
